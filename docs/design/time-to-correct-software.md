# Time to Correct Software

Proposed experimental protocol. Time to Correct Software (TTCS) measures how long a fixed autonomous coding system takes to reach an independently accepted revision under a defined deadline and token budget. Cost to Correct Software (CTCS) measures the corresponding economic cost. Both apply to language and tooling research independently of Splash. Traditional compiler and runtime benchmarks describe the toolchain and artifact. TTCS and CTCS describe the effort of producing the artifact. Measure ordinary engineering and security-sensitive work separately. The [repository baseline](repository-assessment.md#validation-and-performance) provides component measurements. Agent efficacy remains an open question.

Track B starts with the [supported subset](supported-subset.md) and [pilot harness design](ttcs-harness.md) while compiler soundness work proceeds. The harness, sealed fixtures and comparative trials remain to be built and run.

## Language-independent harness

Keep task release, experiment assignment, snapshotting, trace collection, sealed grading and statistical reporting independent of the language. A versioned task manifest defines requirements, eligible files, resource limits and acceptance criteria. Each language adapter supplies a pinned environment, idiomatic authoring commands, build/run or interpretation steps and any language-specific evidence bindings. Use language-neutral behavior oracles and fixture formats where feasible. A new language should require a starter, adapter and equivalence review using the same trial and reporting machinery. Keep Splash-specific queries and policy evidence in the relevant adapter.

## Questions and comparison conditions

1. **Language and toolchain.** Compare Splash with idiomatic Go under each toolchain’s normal conformance and build commands. Go shares Splash’s backend lineage and supplies a practical baseline for the target domain. For policy tasks, also use a strong Go variant with capability-typed interfaces or package isolation, reviewed adapters and equivalent runtime enforcement. Match the requirements and authority budget across languages.
2. **Incremental value of compiler feedback.** Within the same Splash revision and compiler rules, compare human CLI output with structured diagnostics, then add semantic queries and summaries. Wire-format-only and greater-information conditions answer different questions. Report the effects separately. For text versus structured tests, keep available facts and tool permissions equivalent when testing format in isolation. Keep hidden grading outside every condition.
3. **Familiarity and documentation.** Separate a minimal onboarding condition from a condition with curated, version-matched examples and reference material of comparable coverage for each language. Record provided reference tokens and retrieved tokens. Treat pretraining exposure as part of the practical comparison and an uncontrolled factor for claims about inherent language quality.
4. **Ecosystem and design.** Add strict TypeScript as a secondary backend comparator after the first Go run. Add native Rust as a future conventional authoring comparator after the initial Go pilot. Start with matched typed transformations and repair tasks, then add ownership or concurrency workloads only where the requirements are comparable. Use Python for appropriate loosely typed scripting and pipeline workloads with idiomatic verification, and declare any type-checking mode. Report the workload subset for each comparison. Within-language syntax experiments need behaviorally equivalent variants. Cross-language effects blend language, libraries, tooling and model familiarity. [MultiPL-E](https://arxiv.org/abs/2208.08227)

The execution comparison supplies no authoring efficacy evidence.

Build novel, matched tickets and repositories with independently reviewed idiomatic reference solutions. Seed changes from real engineering requirements. Separate authoring and maintenance tasks and use disjoint pilot and holdout instances. Keep public examples for onboarding. For equivalent tasks, use the same public behavior, fixtures, failure conditions and security requirements, with language-appropriate build inputs. Publish task eligibility and unsupported categories to avoid survivorship bias.

Use five initial matched pairs for invoice calculation, shipment validation, inventory feature addition, bug repair in an unfamiliar repository, and a multi-module refactor with supported import forms. Require native builds and hidden behavior checks. This pilot establishes grader validity, instrumentation, task feasibility and observed variance while compiler work continues. It supplies no definitive language comparison.

Give maintenance a separate longitudinal track after the pilot. For example, build a pricing engine, add regional rules, fix rounding, extract a module, add customer discounts, preserve public contracts, then introduce and revise an approval-gated override. Choose an equivalent canonical starting point for each language. In the longitudinal arm, each accepted revision is the next starter and all prior regression criteria remain active. Predefine what happens on failure, such as stopping that trajectory and recording unattempted stages, with any reference-reset study reported separately. Measure cumulative elapsed time and expenditure, regressions and recovery per stage, and the proportion completing the entire sequence. Analyze app trajectories as clusters. Keep independent fresh-checkout trials to help isolate task difficulty from inherited code quality. Separate the conventional sequence and any security-sensitive extension in the report.

## Trial and oracle

A trial starts with a fresh conversation and clean checkout. Wall time starts at task release and includes model inference, local tooling, verification, build and test commands. Take immutable candidate snapshots at common elapsed-time checkpoints and at final submission. Pre-register which candidates count for the primary curve. Additional immutable snapshots after changed-source edits or verification commands can support a finer-resolution sensitivity analysis. Changes between checkpoints can be temporary. Report the schedule, observed interval from the previous sampled failure to the first sampled pass, and the possibility of missed transient successes. The primary time is the timestamp of the first observed accepted candidate, or the deadline if none passes. Report the full checkpoint completion curve and final accepted completion. Grade after the trial with no hidden feedback, and report scoring latency separately.

Predeclare the required gates for each matched task. Record time to static acceptance, native build or equivalent executable readiness, passing all hidden functional and regression tests, and satisfying applicable authority constraints. Only one snapshot meeting all applicable gates qualifies for TTCS. A passing static command with incomplete verification earns only the observed tool milestone. A compiler's missing checks leave acceptance to equivalent independent evidence where the task permits it. If compiler enforcement itself is required and coverage is indeterminate, the candidate fails that gate. The hidden oracle tests observable inputs, outputs and environment state and may examine agreed structural contracts. Use fail-to-pass and pass-to-pass cases. Validate the grader against the starter, multiple valid strategies and plausible incorrect changes. Include negative controls to measure what checks miss. For subjective maintainability, use independent reviewers blind to condition where feasible, report agreement and keep the score separate unless pre-registered as a gate. [SWE-bench Verified task validation](https://openai.com/index/introducing-swe-bench-verified/) · [grader and contamination follow-up](https://openai.com/index/why-we-no-longer-evaluate-swe-bench-verified/)

For policy fixtures, score under the same threat model and initial authority. Use inert data and offline fakes. Execute each candidate in an isolated process or container with bounded resources, no grader secrets, and restricted network and file access. Keep the harness, oracle, trusted compiler and ruleset, immutable snapshots and authority baseline outside agent and candidate write access. The trusted grader runs externally and observes candidate inputs, outputs and controlled fixture state. A compiler acceptance signal alone cannot label an output safe.

Classify observable changes and outcomes without assigning intent. An invalid assignment is an ordinary error. A missing effect declaration is an effect diagnostic. An unnecessary grant or removed approval boundary is a proposed policy change, with the disposition defined by the task. An unresolved call can yield indeterminate verification. A classified payload escaping visible checks is an oracle-detected violation. Report candidate-level occurrences, which checks caught them, remaining violations in the final snapshot, and undetected violations that passed visible checks.

## Metrics and analysis

| Metric | Definition |
| --- | --- |
| Deadline completion and final completion | Share of all trials reaching an accepted checkpoint by the deadline, and share ending with an accepted final submission. Report budget exhaustion and timeouts. |
| Capped TTCS | Mean of min(time to first accepted snapshot, fixed deadline), assigning the deadline to every unsolved run, including early token exhaustion. Report the deadline and completion curve. Median and percentiles among successful runs are descriptive only. |
| CTCS | Total inference and metered execution expenditure across all trials divided by the number of accepted final solutions. Include unsuccessful trials and disclose any shared costs or allocation rules. Publish numerator, denominator, cost per trial and price assumptions. Report no finite estimate when no final solutions are accepted. |
| Semantic context cost | Source and semantic tokens delivered, discovery calls, context growth after initial inspection, relevance samples, and acceptance under fixed context budgets. Record local bytes read separately. |
| First-pass outcomes | Independently grade the first eligible candidate for static check, native build and functional/policy correctness. Record the agent’s first actual check as auxiliary telemetry. |
| Reliability | Hidden-case pass rate, baseline regression rate, and completion of the follow-up change. Report cases, task aggregates and denominators. |
| Repair iterations | Number of source-edit/verification cycles after a failing check or visible test, plus diagnostic code categories and repeated errors. Define grouping in the harness before the trial. |
| Input, output and cost | Total input/output tokens, cached input and reasoning tokens where exposed, reference/context tokens delivered, and inference cost under recorded provider prices. Report local files/bytes read separately. |
| Analysis, native build and test time | Per-command cumulative and per-call latency, with process startup and serialization distinguished from pipeline performance in separate microbenchmarks. Record cache state. |
| Authority outcome | Proposed grant or boundary changes, security-related authoring errors, and observed violations, including caught, final and undetected cases, with tool attribution, witness and oracle. Report rates and counts. |

Use invoiced or reproducible reference prices for model input, cached input, output and metered reasoning where separately billed, plus timed execution at a disclosed machine rate. Report inference and execution components separately, exclude double counting, and publish sensitivity to alternative pricing. CTCS estimates the cost of accepted final deliveries under the measured workflow.

Instrument discovery through observable reads, searches and queries, implementation through edit or patch events, compilation through static and native command timings, and testing through test and fixture invocations. Mark repair windows from a visible failure through the next relevant edit and verification, allowing discovery, compilation and testing within those windows. Use either a mutually exclusive attribution rule with an unclassified bucket or an overlapping report with overlaps disclosed. Keep inference, provider wait and unknown time visible. Derive categories from event logs and reproducible tagging rules, without inferring private reasoning. Report discovery calls, dependency-related errors, causal diagnostic groups, repair rounds and regressions alongside timings. Treat trace differences as explanations to test with controlled ablations.

Block and randomize treatments by task variant, model snapshot and execution window, with repeated independent workspaces. Pin model version and endpoint, harness/prompt template, sampling and inference effort, context and tool budgets, permissions, available commands, reference materials, dependency lockfiles, hardware and CPU/RAM limits. Record cache rules for compiler/build artifacts, dependencies, OS and model prompts. Run separate cold process/cache and standardized warm cache trials. Separate elapsed wall time from model/tool telemetry, including overlap. Batch or balance traffic across providers/time windows and log rate limits. [NIST randomized block designs](https://www.itl.nist.gov/div898/handbook/pri/section3/pri332.htm) · [Infrastructure noise in agentic coding evals](https://www.anthropic.com/research/infrastructure-noise)

Start with four to six matched task pairs and at least three independent runs per arm to validate instrumentation and estimate variance. Then pre-register a smallest effect of interest, completion and safety margins, sample sizing from paired variability, deadline, excluded infrastructure failures and exact analysis. Use more tasks and variants before adding repeated trials alone. Estimate 95% intervals using paired task-cluster bootstrap, stratified by track and model as appropriate, or use matched randomization inference if sample size is small. Retain repetitions inside their task clusters. Report capped time and completion together, denominators and absolute/relative differences, separate policy outcomes, and any adjustments for multiple confirmatory comparisons. Predefine trace-based infrastructure reruns and report sensitivity when counting those cases as failures. Preserve ordinary timeouts and unsuccessful runs. [Kalibera and Jones, rigorous benchmarking](https://kar.kent.ac.uk/33611/45/p63-kaliber.pdf)

## Reproduction and reporting

Publish a run manifest with hashes for compiler, app starter, reference docs, harness and grader, plus invocation, snapshots, seeds when available, provider time window, resource limits, cache policy and tool versions. Capture per-event time, snapshot, command classification, allowed tool outputs, exit status and token/cost telemetry. Keep hidden fixtures sealed until holdout retirement. Release equivalent task specifications, the analysis script and sanitized traces or aggregate tables, documenting any withheld fields. Rerun with more than one model family before generalizing.

An initial report should show each arm’s task counts and exclusions, first-pass build/correctness, final completion with intervals, capped TTCS with intervals, CTCS, context costs, repair iterations, milestone and trace-category timings, regressions, and policy detection/escape counts. Include per-task outcomes and a shared-checkpoint completion curve with sample counts and uncertainty. Keep conventional, security-sensitive and longitudinal outcomes identifiable. Highlight negative and inconclusive results. Synthetic check timings, native throughput and subjective maintainability occupy separate tables.

Threats include contaminated tasks, test ambiguity or overfitting, privilege asymmetry, stronger or weaker baselines, starter quality, researcher expertise, unfamiliar syntax, package maturity, noisy providers, short budgets, harness effects, hidden grader defects and tasks that omit difficult failure modes. Regrade alternative valid solutions, rotate private variants, disclose unsupported outcomes, and run sensitivity analyses by deadline, model, docs and cache. A positive same-Splash tooling effect supports that interface investment. A cross-language advantage requires repeated comparable outcomes and applies first to the tested workload population.

## Feedback into language development

Use pilot traces to propose changes. Recurring import failures suggest testing better module semantics or examples. Excess discovery suggests contract and caller queries. Repeated errors in one causal group suggest a more precise primary diagnostic. Record the hypothesized mechanism and metric before changing the design. Use pilot tasks for iteration and evaluate the change on unseen matched tasks with the frozen oracle. Keep negative and inconclusive results in the decision record.
